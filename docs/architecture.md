# Архитектура

Проект — **монорепозиторий**: устройство, веб-эмулятор и мобильный клиент лежат рядом.
Железо (Raspberry Pi, лампы, датчики) не покупается и эмулируется программно. Код устроен так,
чтобы на настоящей Pi пришлось заменить только драйверы.

```
LightningSystem/
├── docs/        эта документация
├── device/      программа устройства (Python + FastAPI)
├── simulator/   веб-эмулятор: наглядная «квартира» и плата Pi (один HTML-файл)
└── android/     клиент (Java, Android Studio)
```

Клиент обращается **напрямую к устройству** по локальной сети через REST API: адрес IP:порт и API-ключ пользователь вводит вручную.
Отдельного сервера нет: «сервер» — это программа, работающая на самом устройстве.

## Модули устройства (Python)

Код лежит в `device/lighting/<модуль>/`, тесты — в `device/tests/`. Точка входа — `lighting.runtime.main:app`.

| Модуль | Ответственность |
|---|---|
| `domain` | сущности и правила: Объект, Комната, Лампа, Датчик, Замер. Чистые функции: яркость + температура → каналы, плавный переход |
| `hal` | интерфейсы драйверов: `LightDriver`, `SensorDriver`, `PowerMeter`, `Clock` |
| `sim` | виртуальное железо: физика света и мощности, ускорение времени (реализует `hal`) |
| `hardware` | настоящие драйверы для Raspberry Pi: gpiozero (ШИМ, реле) и smbus2 (I2C) (реализует `hal`) |
| `policy` | регуляторы: авто-режим (целевые lux → уставка яркости), циркадный режим (время суток → цветовая температура) |
| `storage` | хранение в SQLite: реестры, комнаты, режимы, уставки, привязки, история |
| `telemetry` | сбор замеров с датчиков, учёт энергии, агрегация за период |
| `service` | сценарии использования: сводит модули вместе, единственное место, где меняется состояние |
| `api` | HTTP-транспорт: роуты, DTO, ошибки, проверка API-ключа (**без логики**) |
| `runtime` | конфиг, выбор `virtual`/`hardware`, фоновые циклы, запуск |

Направление зависимостей — в одну сторону, без циклов:

```
api       -> service
service   -> { domain, policy, storage, telemetry, hal }
policy    -> domain
telemetry -> { domain, storage }
storage   -> domain
sim, hardware -> hal
domain -> (ничего)    hal -> (ничего)    runtime -> всё
```

- `domain`, `hal`, `policy`, `sim` — **чистые** модули: не знают ни про HTTP, ни про базу, ни про asyncio. Их можно тестировать обычными вызовами функций.
- Железо трогают **только** реализации `hal` (`sim`, `hardware`). Остальной код видит интерфейсы.
- `api` не содержит логики: проверяет запрос, вызывает `service`, превращает результат или ошибку в HTTP-ответ.
- Время берётся только через `Clock`: его подменяют в тестах и ускоряют в `sim`.

## Железо (что эмулирует `sim` и чем управляет `hardware`)

| Деталь | Как подключается | Что делает |
|---|---|---|
| **Raspberry Pi** | — | компьютер, на котором работает `device/` |
| **Лампа** — CCT-лента 12 В (тёплые 2700 K + холодные 6500 K светодиоды) | **реле** (вкл/выкл питания) + **2 MOSFET-транзистора** (каналы «тёплый» и «холодный»), каждый на своей ножке GPIO | смешивая два канала, получаем нужную яркость и оттенок белого |
| **Датчик** — TCS34725 (цветовой датчик) | шина **I2C** (два провода: SDA = GPIO2, SCL = GPIO3), адрес `0x29` | меряет освещённость (lux) и цветовую температуру (CCT) |
| **Мультиплексор I2C** TCA9548A | I2C, адрес `0x70` | нужен, если датчиков больше одного: у TCS34725 адрес фиксированный |

Термины:
- **GPIO** — 40 «ножек» на плате Pi. Логика 3.3 В, ток маленький, поэтому ножка только подаёт сигнал, а мощную нагрузку переключают реле и транзисторы. Нумерация **BCM** (GPIO17 = физический контакт 11).
- **ШИМ (PWM)** — ножку очень быстро включают и выключают; доля времени «включено» (duty, 0.0–1.0) задаёт яркость.
- **MOSFET** — электронный «кран»: слабый сигнал с ножки пропускает к ленте нужный ток.
- **Реле** — механический выключатель питания ленты.

Мощность не измеряется, а **рассчитывается** (`PowerMeter` в `sim`). Позже можно добавить настоящий датчик тока INA219 как ещё одну реализацию `PowerMeter`.

Одна CCT-лампа занимает 3 ножки, свободно около 24 → примерно 8 ламп напрямую. Больше — через ШИМ-расширитель PCA9685 (ещё одна реализация `LightDriver`).

## Режимы запуска

`RUNTIME=virtual` (по умолчанию) — драйверы из `sim`, работает на любом ПК.
`RUNTIME=hardware` — драйверы из `hardware`, только на Raspberry Pi.

Какие лампы и датчики физически подключены и на каких ножках/адресах, описывает файл `device/device.yaml`. При первом запуске он заполняет реестры ламп и датчиков. Комнаты создаёт пользователь через API.

## Цикл работы

`runtime` запускает фоновые циклы:

```
каждые 1 с:   датчики -> telemetry (замер, статус онлайн/оффлайн)
              -> policy (авто / циркадный) -> service (новые уставки комнат)
каждые ~30 мс: service -> domain.approach (фактическая яркость плавно идёт к уставке)
              -> LightDriver.set_output (ножки)
каждые 10 с:  PowerMeter -> telemetry (энергия, Вт·ч)
```

Цикл не падает от исключения: ошибка пишется в лог, работа продолжается. При остановке лампы гасятся, ножки освобождаются.

## Модули клиента (Android, Java)

| Модуль | Ответственность |
|---|---|
| `:app` | Activity, навигация, экраны |
| `:core:model` | доменные модели |
| `:core:network` | Retrofit, DTO, маппинг |
| `:core:data` | Repository, настройки, кэш |
| `:feature:*` | экраны по функциям (на старте — пакеты внутри `:app`) |

Контракт с устройством — [api.md](api.md).

## Объём работ

**Основа (к декабрю):**
- комнаты, лампы, датчики, привязки;
- ручное управление: вкл/выкл, яркость, цветовая температура;
- авто-режим по датчику, циркадный режим оттенка;
- плавный переход, учёт энергии и стоимости, история за период;
- API-ключ, `virtual`-режим, веб-эмулятор, Android-клиент.

**Если останется время:** расписания, WebSocket для мгновенных обновлений, мастер подключения новых ламп через API, драйвер PCA9685, датчик тока INA219.
